# Payment tries and the payment timeline page

Status: draft for approval. Date: 2026-11-06.

## Why

A customer contacts a merchant: "my payment failed." The merchant's team needs to see every try, whether 3D Secure passed, and the exact error, either through our API or in the dashboard. Today that history is partly lost, partly hidden from the API, and spread across seven tabs on the payment page.

Success looks like this: a support person opens one page and understands the payment in a single look, and a merchant can get the same try history from the API.

## Goals

1. Keep every provider try and its error, permanently, even if a later try succeeds.
2. Show every try on `GET /v1/payments/{id}`, with its error and 3D Secure result.
3. Include the latest failure in the `payment.failed` webhook.
4. Replace the payment page's tabs with one timeline page.
5. Let operators retry a webhook for one endpoint or redeliver it to all endpoints, including ones added later.

## Non-goals

- Changing tabs on any other dashboard page.
- A webhook for a failed try on a payment that is still open. `payment.failed` keeps firing only when the whole payment fails.
- Backfilling old payments from providers. Old payments show what is already stored.
- A merchant API for redelivering webhooks. Redelivery stays in the dashboard.
- Exposing risk data, customer phone or customer address through this new API work. Those are dashboard additions only.

## Anti-goals

These would make the work a failure even if it technically ran:

- A missing value that looks like a failure. A ✕ appears only when a provider reported a failure.
- A wall of text. The page must be readable at a glance.
- A broken integration. Existing API fields keep their meaning, and all API changes are additive.
- Authentication data, full card numbers, expiry or CVV stored or returned. We store outcomes only.
- History recording that blocks a payment. It stays observational, as `recordStoredProviderPaymentAttempt` documents: a failed history write must never stop reconciliation or booking.

## Decided by the user

- Merchants can see every try through the API, including 3D Secure success or failure.
- The page uses layout A: one timeline, with no tabs.
- The page shows phone, address, risk review, card and bank details, and name on card where provided.
- Risk shows each check as a tick or cross: address, ZIP/postal and so on.
- The page uses as little text as possible.
- Webhooks can be retried, and redelivery reaches all endpoints, including newly added ones.

## Piece 1: saving tries and the API

### Vocabulary

- **Attempt**: Paymux's existing `payment_attempts` row. Its meaning does not change.
- **Try**: one go at paying at the provider. An attempt has zero or more tries.

### Storage

Extend `provider_payment_attempts` to hold the method details, risk details and 3D Secure status of each try. Add the migration for both SQLite and Postgres.

Required behavior:

- Every path that applies a provider snapshot records the try, including reconciliation and subscriptions. Prefer one shared place over patching each caller.
- A recorded failure is never erased. A row's failure code and message survive a later update.
- Stripe needs its own key per try, because retries in a Checkout Session can share a payment intent and today's primary key would merge them. The lookups by provider payment ID in `internal/store/connectors.go:210` and `internal/store/recon.go:238` must keep working.

### Connectors

- **Stripe**: subscribe to `payment_intent.payment_failed`, read `card.three_d_secure` and the address, postal and CVC checks, and record each failed try. Existing accounts must get the new subscription through the existing webhook configuration path. As we recall, a failed authentication may create no charge, so listing charges alone may miss it. Confirm this with the Stripe sandbox tests.
- **Razorpay**: read `error_source`, `error_step` and `error_reason` if they exist, and map an authentication-step failure to 3D Secure `failed`. These field names come from memory and must be verified against real responses first.
- **Whop**: map the existing `three_d_secure` boolean. `false` means `not_verified`, never `failed`, matching `internal/dashboard/risk.go`.
- **PayU**: capture `name_on_card`.
- **Cashfree, PayU, Zoho, remote**: check real responses and fill in what they send. If a provider sends nothing, record nothing.

Add a name field to `connector.CardDetails`. Remote connectors must keep working when it is absent.

### API

`GET /v1/payments/{id}` keeps every current field. Each attempt gains `tries`, oldest first:

```json
{
  "id": "att_...",
  "status": "pending",
  "tries": [
    {
      "provider_payment_id": "...",
      "status": "failed",
      "method": "card",
      "method_details": { "card": { "last4": "4242", "network": "visa", "issuer": "...", "name": "..." } },
      "three_d_secure": { "status": "passed" },
      "failure_code": "insufficient_funds",
      "failure_message": "Your card has insufficient funds.",
      "created_at": "2026-11-06T16:07:00Z"
    }
  ]
}
```

- `three_d_secure.status` is `passed`, `failed` or `not_verified`. If the provider reported nothing, leave the object out.
- `status` on a try uses Paymux's normalized values, not the provider's raw text. Today's table stores raw status, so the builder must map it; `providerAttemptStatus` in `internal/reconcile/reconcile.go:121` is a starting point.
- Missing values are left out, never empty strings.
- `tries` is an empty list when there are none, for example on a `checkout_error`, where the attempt's own failure fields still explain what happened.
- An attempt's `failure_code` and `failure_message` still clear on capture, so "current state" keeps its meaning. History lives in `tries`.
- Name on card is available to any key with `payments:read`. Update the `PaymentMethodDetails` description in `docs/openapi.yaml`.

### `payment.failed` webhook

Add `failure_code` and `failure_message` from the attempt that caused it, to `paymentEventData` in `internal/core/views.go:79`. Leave them out on other event types.

### Name on card

This is personal data. It must stay out of logs (`internal/redact` already treats cardholder names as sensitive; add a test). A search found no customer-data erasure feature to extend, so storing it adds no new erasure work today. For Stripe, only use a field that really is the name on the card, and do not relabel billing details as such.

## Piece 2: the payment page

Mockups: [full payment](../../design/paymux/payment-timeline.png) and [provider sends little](../../design/paymux/payment-timeline-sparse.png). Tries, customer and risk values in them are sample data.

### Layout

- **Header**: payment ID, status, large amount.
- **Top row of tiles**: Last failure, Tries, Risk, Webhooks, Received.
- **Left**: the timeline.
- **Right**: Customer, Risk, Payment, then Sync and Refund. On phones this moves below the timeline.

### Timeline

Shown by default, in time order: created, checkout started, each try, refunds and webhooks. "All events" adds ledger and system events to the same list.

- Say "Checkout started", never "customer opened checkout". We only know a checkout was created.
- A try shows the error in red, then card, bank and name on card, then ✓/✕ badges and the failure code.
- "Provider IDs and logs" opens within a try, and also shows that try's risk checks.
- A failed attempt with no tries still appears, using the attempt's own failure.
- With no tries, say "The customer hasn't tried to pay yet."

### Right side

- **Customer**: name, email, phone, address; merchant customer ref, legal name and GSTIN if present.
- **Risk**: Address, ZIP/postal, CVV and 3D Secure as ticks or crosses, then location, IP and auth code, for the latest try with risk data. The score appears only in the top tile.
- **Payment**: app, refunded, order ref, description, flags.

### Missing data

| Missing | Shown |
|---|---|
| All risk data | Risk tile "Not provided" in grey, no Risk panel |
| Some checks | Only those received |
| Score not yet in | Tile "Pending", or "Not scored" for a failed try, as `paymentRiskView` does |
| Failure reason | "No reason given". Note that `ToSnapshot` fills the code with the status, so a code of `failed` with no message counts as no reason |
| Card, bank or name | What we have, or just "Card" |
| 3D Secure | No badge |
| Phone or address | Only the lines we have |

### Actions that move

- **Refund**: a pop-up, opened from the right side.
- **Resend**: on each webhook in the timeline.
- **Send status webhook**: stays available to users with `webhook.replay`; placement is the builder's call.
- **Logs link and simulator**: logs stay reachable, and simulator tools move to "Test tools", shown only on simulator payments.

Every existing action and permission check must survive the move. Custom roles can have `webhook.replay` without `payment.read`; see `webhookResendSubmit`.

### Webhooks

Each event in the timeline lists its endpoints as ✓ status, ✕ status, or **New / Not sent**.

- **Redeliver to all (n)** calls `ResendEvent`. It reaches every enabled endpoint in the same mode that accepts the event type, including new ones and ones that already succeeded, with the same `webhook-id`. Disabled, other-mode and unsubscribed endpoints are excluded and not counted in `n`.
- **Retry** calls `ReplayDelivery` for one endpoint, shown only on failed ones.

**Required backend change:** an endpoint waiting for its next automatic retry has status `pending`, and both calls refuse or skip it today. Both must send immediately in that case and replace the scheduled retry, so one delivery does not go out twice. The dedupe key is per attempt (`outbound.go:124`), so simply enqueuing again is not safe: a leftover scheduled job can fire later or swallow the next retry. A delivery actually in flight is still refused or skipped, and the page says so.

The redeliver count must match what is actually sent.

## Testing

- Failure kept after a later success, on the same and on different provider IDs.
- Every snapshot path records a try, and a history write failure does not block booking.
- API: additive shape, missing fields left out, old attempts without tries.
- Each connector's real or fixture responses map to the right 3D Secure and risk values; Whop `false` is never `failed`.
- Retry now while a retry is scheduled: exactly one delivery per send, and later retries still work if it fails again.
- Page: full, sparse and no-tries states, phone width, permissions, and every moved action. Check the peek pane (`frontend/dashboard/src/peek-pane.tsx`), which also renders payment pages.
